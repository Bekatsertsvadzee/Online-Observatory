# Darkview observatory adapter protocol

## Purpose

`ObservatoryAdapter` is the server-only boundary between Darkview cloud orchestration and an observatory agent. It describes Darkview’s domain operations without assuming a telescope manufacturer, transport, or device command set.

No Celestron, CPWI, ASCOM, or Alpaca command is implemented here. A real integration must be based on confirmed vendor documentation and tested equipment before `RealObservatoryAdapter` is replaced.

## Trust boundary

The browser never creates an adapter instance and never sends credentials to physical equipment. Before a mutating adapter method is called, the server orchestration layer must verify:

1. authenticated user and database role;
2. active mission and session ownership;
3. valid, unrevoked telescope lease;
4. unexpired command;
5. observatory readiness;
6. server-side safety approval.

The adapter validates its command envelope again, but it does not replace the authorization policy in `command-authorization.ts`. Observatory credentials, endpoint addresses, and vendor tokens belong only in the future real adapter’s server environment.

## Operations

| Method                        | Kind    | Contract                                                                               |
| ----------------------------- | ------- | -------------------------------------------------------------------------------------- |
| `getStatus()`                 | Query   | Returns connection, telescope, active mission, observation time, and simulation marker |
| `getCurrentTarget()`          | Query   | Returns the adapter’s current normalized target or `null`                              |
| `getCoordinates()`            | Query   | Returns normalized J2000 equatorial coordinates or `null`                              |
| `startMission(command)`       | Command | Assigns a mission and begins tracking the supplied normalized target                   |
| `abortMission(command)`       | Command | Stops the matching active mission and leaves the simulator parked                      |
| `park(command)`               | Command | Places the telescope in its safe parked state                                          |
| `capture(command)`            | Command | Requests one capture using a consumer processing preset                                |
| `getPreview()`                | Query   | Returns sanitized preview metadata or `null`; it does not expose camera credentials    |
| `getMissionEvents(missionId)` | Query   | Returns ordered, data-driven adapter events for one mission                            |

Queries are side-effect free and do not use command envelopes. Every mutating operation uses the following envelope:

| Field       | Meaning                                                         |
| ----------- | --------------------------------------------------------------- |
| `commandId` | Globally unique idempotency key generated by trusted cloud code |
| `missionId` | Mission authorizing the operation                               |
| `userId`    | Authenticated actor recorded for authorization and audit        |
| `issuedAt`  | ISO 8601 issuance time                                          |
| `expiresAt` | ISO 8601 deadline after which a new command must be issued      |

An envelope is invalid when a required identifier is blank, a timestamp is malformed, `expiresAt <= issuedAt`, or `issuedAt` is in the future. A previously unseen command is rejected with `COMMAND_EXPIRED` when `expiresAt` is at or before the adapter clock.

## Idempotency

`startMission`, `abortMission`, `park`, and `capture` are idempotent by `commandId`.

- The first accepted command stores its canonical operation and payload with the result promise.
- A concurrent or later retry with the same `commandId` and equivalent payload receives the original result.
- A retry does not create another capture or mission event, even after the original command expires.
- Reusing a `commandId` for a different operation or payload fails with `IDEMPOTENCY_CONFLICT`.
- Failed commands are not retained, allowing a corrected command with a new valid envelope to be attempted.

The in-memory simulator ledger is development-only. A production observatory agent must persist idempotency records and command receipts across restarts before hardware integration is enabled.

## Simulator behavior

`SimulatorObservatoryAdapter` is deterministic when supplied with a clock. It begins `READY` and `PARKED`, keeps mission events in memory, and returns cloned query data so callers cannot mutate adapter state.

Every simulator status, receipt, preview, and event is marked with `simulated: true` or `source: "SIMULATOR"`. Simulator results must retain the visible **SIMULATED OBSERVATORY** label in product UI and logs. They must never be copied into a real-hardware audit stream without that marker.

The simulator models Darkview domain outcomes only. It does not emulate mount packets, camera drivers, CPWI, ASCOM, Alpaca, or undocumented Celestron behavior.

## Real adapter fail-closed behavior

`RealObservatoryAdapter` is deliberately non-operational. Every query and command throws:

```text
code: NOT_CONFIGURED
message: Real observatory protocol is not configured
```

It must not return an offline snapshot, a successful receipt, synthetic target data, or simulator output. This prevents a deployment from appearing connected to physical hardware before a protocol is confirmed.

## Error codes

| Code                   | Meaning                                                |
| ---------------------- | ------------------------------------------------------ |
| `NOT_CONFIGURED`       | No verified real observatory protocol is installed     |
| `INVALID_COMMAND`      | Envelope, target, or coordinates failed validation     |
| `COMMAND_EXPIRED`      | A new command arrived after its deadline               |
| `IDEMPOTENCY_CONFLICT` | A command ID was reused with different data            |
| `MISSION_CONFLICT`     | Another mission is already active                      |
| `NO_ACTIVE_MISSION`    | The command does not match a currently tracked mission |

Errors include the adapter operation name and are safe for server logs. Public APIs should translate them to stable consumer messages without exposing internal endpoints or credentials.

## Requirements before a real implementation

- Select and cite the exact documented CPWI, ASCOM, or Alpaca API and supported versions.
- Confirm authentication, TLS, network isolation, timeouts, and reconnect behavior.
- Map each Darkview domain operation to documented protocol calls.
- Implement durable idempotency, command audit storage, and ordered mission events.
- Add simulator-backed contract tests and hardware-in-the-loop tests for movement limits, Sun avoidance, abort, and park behavior.
- Require explicit operator review before enabling the adapter in production.
